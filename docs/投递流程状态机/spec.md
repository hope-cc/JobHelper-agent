# 投递流程状态机 Spec

## 背景

当前 SubmitFlow（简历投递 8 步流程）完全依赖 LLM 在对话中自编排：

- 执行顺序由 LLM 临场决定，只能靠 `_SUBMIT_FLOW_NEXT` 注入 `<system-reminder>` 提醒「诱导」LLM 继续下一步。LLM 时常误判任务已完成、未到 10 次工具循环上限就提前收尾，长流程容易执行到一半就结束。
- 图状态每轮由 `chat/graph.py` 新建，`browser_snapshot`、`getPersonalInfo` 的结果不跨轮保留。同一会话里对同一个 URL 反复 `browser_snapshot`、反复 `getPersonalInfo`，既慢又浪费 token。
- 浏览器侧的真实状态（已识别表单结构、已填基础字段、已探测的下拉选项）没有结构性缓存，无法在后续轮次复用。

用户希望把投递过程改造成 langgraph 内的**确定性状态机**：用 `current_stage` 控制条件边，8 个步骤各自为节点；浏览器快照、个人信息、下拉选项等缓存在图状态里，跨轮持小、去重复用。

## 目标

- **G1**：投递流程成为确定性状态机。执行顺序由 `current_stage` 条件边决定，不依赖 LLM 记住「下一步该做什么」。
- **G2**：同一 URL 的 `browser_snapshot`、同一会话的 `getPersonalInfo` 在流程内只取一次。
- **G3**：流程状态（URL、当前阶段、表单字段、已填字段、个人信息、下拉选项）随会话持久化，支持「等用户登录」「等用户选简历」等多轮等待交互。
- **G4**：保留 LLM 在决策点做语义判断（字段→数据键映射、下拉选项→个人信息值映射），但浏览器操作执行顺序由状态机保证。
- **G5**：敏感字段真实值不进对话历史、不进 LLM 决策上下文（仅提供脱敏视图或数据键）。

## 功能需求

- **F1（入口，LLM 识别意图）**：在普通对话中，LLM 识别到用户投递意图时调用 `browser_navigate` 作为**唯一入口**。调用成功后，流程由状态机接管，LLM 不再编排后续步骤。
- **F2（确定性状态机）**：投递流程由 8 个顺序节点组成（导航等登录、快照表单、上传简历、再快照、取个人信息、填写基础字段、探测下拉框、填写下拉框）。图用 `current_stage` 控制条件边，每步只做一件事并写回状态。
- **F3（阶段持久化）**：投递流程专用状态（`job_url`、`current_stage`、表单字段、未填字段、上传入口、已上传简历、候选清单、个人信息脱敏视图、下拉探测结果、各计划的映射）随会话存入会话文件。每轮请求以持久化的阶段为起点恢复。
- **F4（流程内去重）**：同一 URL 的 `browser_snapshot` 在流程中只调用一次；`getPersonalInfo` 在流程中只调用一次。后续轮直接读状态缓存，不再重复请求同一工具。
- **F5（LLM 决策点）**：两类语义判断由节点内的受控 LLM 调用产出，LLM 只输出映射计划、不直接驱动浏览器：
  - 表单填充计划：根据未填控件列表 + 个人信息数据键，产出 `[{ref, data_key}]`
  - 下拉框填充计划：根据下拉选项列表 + 个人信息值，产出 `[{ref, data_key 或 value}]`
- **F6（敏感信息保护）**：真实的姓名、电话、证件号等敏感值不写入对话历史。状态中保存的是**脱敏视图**（与 `getPersonalInfo` 一致的 `***` 替换）；真实值只在工具执行时从本地 `profile.json` 读取。
- **F7（等待交互）**：`waiting_login` 与 `waiting_resume_choice` 两个阶段等待用户回复后继续；`waiting_resume_choice` 时用户可直接回复候选简历序号或文件名。
- **F8（结果汇报）**：每步完成后向用户输出简短的进度文本（如「已填写基础字段：姓名***、电话***」）；流程结束输出「表单填写完成，请检查后提交」。
- **F9（错误处理）**：状态机执行中遇工具错误（浏览器未连接、无个人信息等）时，以错误提示结束本轮，并清除流程状态回到普通对话，用户可以重新发起投递。

## 非功能需求

- **N1（确定性）**：同样的输入状态与浏览器上下文重复执行，产出相同的步骤序列。步骤顺序不依赖 LLM 临场决策。
- **N2（协议兼容）**：文本流式事件仍通过 `stream_writer` / SSE 透传前端，前后端事件协议不变。
- **N3（持久化恢复）**：服务重启后，会话仍可从已持久化的阶段恢复，等待点不丢失。
- **N4（无新硬依赖）**：不引入 langgraph checkpointer / MemorySaver / 新的数据库；沿用现有 JSON 会话存储（`data/conversations`）。
- **N5（不退化普通对话）**：普通（非投递）对话的 ReAct 行为与工具集完全不受影响。

## 不做的事

- **不做**浏览器表单的**自动提交**：最后一步完成后仍由用户手动「提交」。
- **不做**对 `browser_navigate` 以外的浏览器工具做状态机编排（点击翻页、搜索等仍走普通 ReAct）。
- **不做**前端改动。
- **不做**多会话间共享流程状态（一个会话一套投递流程）。
- **不做**简历多份自动选择（多份时等待用户选择，这是既有行为）。
- **不做**将 `personal_info` 真实值持久化到会话（仅存脱敏视图）。

## 验收标准

- **AC1**：用户在普通对话说「帮我投递 <URL>」，LLM 调用 `browser_navigate` 后，流程进入状态机；此后回复「继续」不再需要 LLM 编排队。
- **AC2**：等待登录阶段持久化状态中包含 `current_stage="waiting_login"` 与 `job_url`；服务重启后回复「继续」仍能从同一阶段恢复执行。
- **AC3**：流程内 `browser_snapshot` 对该 URL 仅调用一次、`getPersonalInfo` 仅调用一次。可通过日志/桩验证。
- **AC4**：存在多份简历时，流程停在 `waiting_resume_choice` 并提示候选；用户回复序号或文件名后继续上传。
- **AC5**：基础字段填写与下拉框填写两个决策点各只产生一次 LLM 映射调用；其输出为映射计划，由状态机执行。
- **AC6**：整个流程的 `messages`/LLM 决策上下文中不出现真实敏感值（姓名、电话、证件号等以 `***` 或数据键出现）。
- **AC7**：浏览器不可用等错误时，本轮输出明确错误提示并停止流程，之后回到普通对话。
- **AC8**：普通对话（非投递）仍然正常，既有 `chat_node`/`tool_node` ReAct 行为与工具集不变。
- **AC9**：完成流程后最终输出提醒用户检查并手动提交。

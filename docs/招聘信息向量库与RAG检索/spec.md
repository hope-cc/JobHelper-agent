# 招聘信息向量库与 RAG 检索 Spec

## 背景

JobHelper 通过 `dispatchTasks` 把批量抓取任务交给子 agent 池。子 agent 解析招聘简章，以职位为单位输出 JSON 数组（字段：公司/职位/工作职责/任职要求/工作地点/投递方式）。

目前子任务结果堆积在 `_result_queue`，依赖调用方主动 drain（该调用已注释），结果既不被消费也不持久化——重启或换会话后，抓到的职位信息即丢失。

## 目标

- G1 子任务结果自动、异步入库，无需用户发消息触发
- G2 向量库持久化到 `data/vector`，进程重启后数据仍在
- G3 主 agent 获得 RAG 查询工具：问题 → embedding → BM25+向量混合检索 → RRF 排序 → 返回职位
- G4 按「公司+职位」去重，防止重复入库

## 功能需求

- **F1 自动入库** — 调度器后台持续监控结果队列，新结果到达即尝试解析；解析为 JSON 数组且含「公司、职位」字段的职位逐条写入向量库；解析失败/格式非法则跳过并记录，不影响后续结果。
- **F2 向量库持久化** — chromadb 持久化客户端，数据目录 `data/vector`，每个职位一条记录。
- **F3 去重** — 以「公司+职位」为唯一键，已存在则不重复写入；去重集合在进程启动时从现有向量库重建。
- **F4 嵌入生成** — 调用本地 ollama 的 bge-m3 生成职位文本向量。
- **F5 RAG 查询工具** — 注册为主 agent 可调用工具。输入用户问题（可选 top_k），内部完成 问题→向量、混合检索（BM25 + 向量）、RRF 融合排序，返回 top_k 条职位记录（含全部字段）。
- **F6 边界处理** — 向量库为空或 ollama 不可用时，查询工具返回明确可读提示，不导致对话中断。

## 非功能需求

- **N1 不阻塞对话** — 入库在后台协程进行，主 agent 对话流不受影响。
- **N2 并发安全** — 入库与检索并发执行无竞态。
- **N3 可配置** — ollama 地址、嵌入模型名、默认 top_k 支持配置，带合理默认值。
- **N4 幂等** — 同一「公司+职位」重复出现不产生重复记录。

## 不做的事

- 不做职位记录的更新/覆盖（键相同则直接跳过）
- 不做向量库的管理界面或删除功能
- 不做子任务结果注入对话（已确认移除）
- 不做分块/引用溯源（每条职位记录即天然文档单元）
- 不做跨进程多实例的分布式去重
- 不做检索结果的持久化或会话缓存

## 验收标准

- **AC1** 派遣子任务后，无需用户再发消息，职位自动写入 `data/vector`；重启进程后记录仍在。
- **AC2** 相同「公司+职位」再次出现在结果中，向量库不产生重复记录。
- **AC3** 主 agent 可调用 RAG 查询工具，传入问题，返回按相关性排序的职位 JSON 列表（含全部字段）。
- **AC4** 检索结果同时受关键词匹配与向量相似度影响（混合检索与 RRF 生效）。
- **AC5** 向量库为空或 ollama 不可用时，查询工具返回可读提示，不导致对话报错。

## 环境前置

- 需手动执行 `ollama pull bge-m3`（当前 ollama 无任何模型）
- Python 侧无需新装依赖（chromadb / requests 已具备）
